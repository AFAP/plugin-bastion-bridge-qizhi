# 通用堡垒机 SSH 桥接器需求说明

> 本文档面向开发者，描述如何为任意堡垒机产品开发一个「专用 SSH 桥接 EXE」。
> 阅读者不需要了解本项目具体实现，只需要按照本文档的需求逐项实现，即可得到可用的桥接器。

---

## 1. 项目背景与目标
### 1.1 背景

各类堡垒机（天玥、齐治、网御星云、深信服、绿盟、H3C 等）为了兼容用户习惯，通常允许在 Web 控制台点击 SSH 资源时唤起本地安装的通用 SSH 客户端，如：

- plink.exe
- putty.exe
- SecureCRT.exe
- Xshell.exe

这些通用客户端只能提供人机交互式终端，**无法让 AI 程序稳定地发送命令并获取结构化返回结果**。

### 1.2 目标

开发一个**专用桥接 EXE**，替代上述通用客户端。该 EXE 被堡垒机唤起后，完成以下三件事：

1. **接收并解析**堡垒机传递的连接参数（目标主机、端口、用户名、密码、会话名等）。
2. **建立 SSH 连接**到目标 Linux/Unix 服务器。
3. **暴露本地 API/Websocket 服务**，供 AI 助手调用以执行命令、流式获取输出、发送交互式输入。

---

## 2. 总体需求

### 2.1 桥接器 = SSH 客户端 + 本地 API 网关

```text
┌─────────────────┐      唤起并传参      ┌─────────────────┐
│   堡垒机 Web     │  ───────────────▶  │   专用桥接 EXE   │
│   控制台         │                    │  (本需求描述产物) │
└─────────────────┘                    └────────┬────────┘
                                                │
                          SSH 连接              │
                                                ▼
┌─────────────────┐    HTTP/WebSocket 本地 API  ┌─────────────────┐
│    AI 助手       │  ◀──────────────────────▶  │   目标服务器     │
│ (本机 127.0.0.1) │                           │   (Linux/Unix)  │
└─────────────────┘                           └─────────────────┘
```

### 2.2 必须满足的原则

| 原则 | 说明 |
|---|---|
| **单一文件 EXE** | 最终交付物为单个 `.exe` 文件，便于复制替换。 |
| **无管理员权限** | 运行和日志写入均应在用户目录下，不依赖管理员权限。 |
| **本地唯一 API** | API 仅监听 `127.0.0.1`，不暴露到外部网络。 |
| **防御性编程** | 参数解析失败、SSH 连接失败都不能让进程直接退出；应进入诊断模式并保留 API。 |
| **可观测** | 所有参数、连接过程、命令执行、错误必须写入日志。 |

---

## 3. 功能需求

### 3.1 入口层需求

#### FR-001 被堡垒机唤起

桥接 EXE 必须能被堡垒机通过标准 Windows 进程创建机制唤起，接收命令行参数 `sys.argv`。

#### FR-002 控制台 UTF-8

EXE 启动后应将控制台输出编码设置为 UTF-8，确保中文路径、用户名、命令输出不乱码。

#### FR-003 记录原始参数

必须将所有 `sys.argv` 完整写入日志，作为后续适配新厂商的第一手资料。

#### FR-004 参数解析失败不崩溃

即使参数解析失败，也应启动本地 API，并通过 `/health` 接口返回 `connected=false` 及错误信息。

#### FR-005 SSH 连接失败不崩溃

如果 SSH 连接失败，也应启动本地 API，供用户查询状态和日志。

---

### 3.2 参数解析层需求

#### FR-007 归一化为通用连接对象

无论堡垒机传参格式如何，必须解析成统一的数据结构：

```python
class ConnectionParams:
    host: str           # 真实 SSH 目标主机
    port: int           # 真实 SSH 目标端口
    username: str
    password: Optional[str]
    protocol: str       # 默认 "ssh2"，可选 "ssh1" / "telnet"
    key_path: Optional[str]
    bastion_host: Optional[str]
    extra: Dict[str, str]   # 厂商特定字段（会话名、配置目录等）
```

#### FR-008 支持多种传参风格

参数解析器应至少支持以下常见风格，并易于扩展：

| 风格 | 示例 |
|---|---|
| SecureCRT 会话式 | `/S session_name host /L user /PASSWORD pass /P port /F config_dir` |
| SecureCRT 老式 | `/SSH2 /L user /P pass host:port` |
| PuTTY 显式 | `-ssh user@host -P port -pw pass` |
| PuTTY 会话文件 | `-load tmp:C:\path\session.txt -pw pass` |
| GNU 长选项 | `--host host --port port --user user --password pass` |
| SSH URL | `ssh://user:pass@host:port` |

#### FR-009 会话配置文件解析

如果堡垒机通过 `-load tmp:<file>` 这类形式传递临时会话配置文件，EXE 必须能读取并解析文件中的 `HostName`、`PortNumber`、`UserName` 等字段。

#### FR-010 未知参数记录

不认识的参数应记录到日志的 `extra` 字段中，便于后续扩展。

---

### 3.3 SSH 引擎层需求

#### FR-011 建立 SSH 连接

使用 SSH 客户端库（如 Paramiko）与目标主机建立连接，支持密码认证、密钥认证、SSH Agent。

#### FR-012 兼容旧算法

必须兼容老旧 SSH 服务器常用的 KEX/加密/MAC 算法，例如：

- `diffie-hellman-group14-sha1`
- `diffie-hellman-group1-sha1`
- `ssh-rsa`
- `aes128-cbc`、`3des-cbc`
- `hmac-sha1`

#### FR-013 自动接受主机密钥

首次连接目标主机时，不应因主机密钥确认而卡死。可采用 `AutoAddPolicy()` 策略。

#### FR-014 执行单次命令

提供 `execute(command, timeout)` 方法，返回：

```python
{
  "stdout": str,
  "stderr": str,
  "exit_code": int
}
```

#### FR-015 支持 exec_command 与交互式 shell 两种模式

部分服务器不支持 `exec_command`，只支持交互式 shell。桥接器应：

1. 优先尝试 `exec_command`；
2. 如果返回结果仅为登录横幅或执行失败，自动降级到交互式 shell 执行；
3. 交互式 shell 执行应复用连接时已打开的持久 shell 通道，避免并发通道限制。

#### FR-016 流式输出

提供 `stream_execute(command)` 方法，以生成器方式实时产出 `stdout` / `stderr` 数据块，命令结束时产出 `exit` 事件。

#### FR-017 交互式输入

提供 `send_input(data)` 方法，向当前交互式 shell 通道发送数据（如确认 `y/n`、sudo 密码等）。

#### FR-018 连接状态查询

提供 `is_connected()` 方法，供 API 层返回健康状态。

---

### 3.4 AI 接口层需求

#### FR-019 本地 HTTP 服务

启动一个仅监听 `127.0.0.1` 的 HTTP 服务，推荐端口 `8765`（各厂商桥接应使用不同默认端口避免冲突）。

#### FR-020 健康检查端点

```http
GET /health
```

返回：

```json
{
  "status": "ok",
  "connected": true
}
```

#### FR-021 单次命令端点

```http
POST /execute
Content-Type: application/json

{
  "command": "df -h",
  "timeout": 30
}
```

返回：

```json
{
  "stdout": "...",
  "stderr": "",
  "exit_code": 0
}
```

#### FR-022 流式输出端点

```http
GET /stream?command=dmesg%20%7C%20tail
```

以 SSE 或类似方式返回实时输出。

#### FR-023 交互式输入端点

```http
POST /input
Content-Type: application/json

{
  "data": "y\n"
}
```

#### FR-024 WebSocket 接口（可选但推荐）

提供 WebSocket `/ws`，支持事件：

- `command`：执行命令并返回结果
- `stream`：流式执行
- `input`：发送交互输入

#### FR-025 端口发现文件

实际监听地址写入固定文件：

```text
%LOCALAPPDATA%\sshbridge\<AppName>\active_port.txt
```

内容示例：

```text
127.0.0.1:8765
```

---

### 3.5 配置与日志需求

#### FR-026 本地配置文件

配置文件路径：

```text
%LOCALAPPDATA%\sshbridge\<AppName>\config.json
```

至少支持以下配置项：

```json
{
  "api_host": "127.0.0.1",
  "api_port": 8765,
  "ssh_connect_timeout": 15,
  "retry_connect": true,
  "retry_max_attempts": 3,
  "retry_delay_seconds": 2,
  "log_level": "INFO",
  "keepalive_enabled": true,
  "keepalive_interval_seconds": 60,
  "keepalive_command": "ls"
}
```

#### FR-027 日志文件

日志路径：

```text
%LOCALAPPDATA%\sshbridge\<AppName>\logs\bridge.log
```

日志应使用滚动文件，避免无限增长。

#### FR-028 日志内容

必须记录：

- EXE 启动时间、Python 版本、接收到的原始 `sys.argv`
- 参数解析结果
- SSH 连接过程及错误
- API 请求摘要
- 命令执行结果及退出码

#### FR-029 空闲保活

当配置时间内未收到任何命令时，自动执行一个无害命令（如 `ls`），防止堡垒机/隧道因空闲超时而断开。

## 4. 非功能需求

### 4.1 性能

| 需求 | 说明 |
|---|---|
| NFR-001 启动时间 | 从被唤起到 API 可响应，应小于 5 秒（不含 SSH 握手）。 |
| NFR-002 命令延迟 | 单次命令从发送到返回，应小于 2 秒（不含命令自身执行时间）。 |
| NFR-003 并发 | 同一时刻只处理一个命令请求；流式和输入请求应串行化。 |

### 4.2 安全

| 需求 | 说明 |
|---|---|
| NFR-004 本地监听 | API 必须仅绑定 `127.0.0.1`，禁止 `0.0.0.0`。 |
| NFR-005 密码保护 | 日志中所有密码、密钥内容必须脱敏为 `***` 或不记录。 |
| NFR-006 不持久化凭证 | 不把密码写入除日志以外的任何文件。 |

### 4.3 可靠性

| 需求 | 说明 |
|---|---|
| NFR-007 单文件 | 最终产物为单文件 EXE，不依赖额外 DLL 或配置文件即可运行。 |
| NFR-008 无弹窗 | 正常运行时不应弹出命令行窗口或异常对话框干扰用户。 |
| NFR-009 进程生命周期 | SSH 连接建立后，进程应保持运行直到用户关闭或 SSH 断开。 |

### 4.4 可维护性

| 需求 | 说明 |
|---|---|
| NFR-010 模块化 | 入口、参数解析、SSH 引擎、API 接口应分层清晰，便于替换。 |
| NFR-011 厂商隔离 | 不同厂商的桥接器应放在各自目录，互不干扰。 |
| NFR-012 可扩展 | 新增厂商时，主要工作应集中在参数解析层，其他层尽量复用。 |

## 5. 适配新厂商的步骤

为一家新的堡垒机开发桥接器时，建议按以下顺序进行：

1. **创建专属目录**
   
   例如：`网御星云堡垒机/`

2. **复用通用模块**
   
   复制以下模块到该目录：
   - `connection.py`
   - `config.py`
   - `logger.py`
   - `ssh_client.py`
   - `api_server.py`
   - `requirements.txt`

3. **实现参数解析器**
   
   编写新的 `params.py`，将厂商特定参数转换为 `ConnectionParams`。

4. **调整入口程序**
   
   编写新的 `main.py`，修改应用名称、默认端口、日志目录等。

5. **创建打包配置**
   
   创建新的 `.spec` 文件和 `build.bat`，输出文件名需与堡垒机期望的文件名一致（如 `putty.exe`、`SecureCRT.exe` 等）。

6. **抓取真实参数**
   
   在堡垒机中配置临时日志版 EXE，点击 SSH 资源，记录真实 `sys.argv`，据此完善 `params.py`。

7. **构建并测试**
   
   运行 `build.bat` 生成 EXE，替换到堡垒机指定位置，测试命令执行。

## 6. 验收标准

一个桥接器可以交付使用，必须满足：

1. 能从对应堡垒机 Web 控制台被正常唤起。
2. 能正确解析堡垒机传递的参数并成功建立 SSH 连接。
3. `GET /health` 返回 `connected: true`。
4. `POST /execute {"command": "uname -a"}` 返回真实的服务器输出及 `exit_code: 0`。
5. 空闲 1 分钟后，SSH 连接不自动断开。
6. 日志文件中能查到参数解析、连接、命令执行的完整记录，且密码已脱敏。
7. 进程退出后，不遗留僵死进程或端口占用。

## 7. 术语表

| 术语 | 说明 |
|---|---|
| 堡垒机 | 运维安全网关，集中管理服务器访问权限的中间系统。 |
| 桥接器 | 本需求描述的专用 EXE，替代通用 SSH 客户端，为 AI 提供本地 API。 |
| `exec_command` | SSH 协议中的非交互式命令执行通道。 |
| 交互式 shell | SSH 协议中的伪终端会话，类似手动登录后的 shell。 |
| MOTD | Message of the Day，登录后显示的欢迎/提示信息。 |
| SSE | Server-Sent Events，一种服务器向浏览器单向推送的技术。 |

## 8. 参考实现

本仓库即是本规范的参考实现：**齐治堡垒机** 桥接器，输出 `putty.exe`，
技能插件位于 `skill/qizhi-bastion/`。对应关系：

| 需求章节 | 实现模块 |
|---|---|
| 3.1 入口层 | `main.py` |
| 3.2 参数解析层 | `params.py`、`connection.py` |
| 3.3 SSH 引擎层 | `ssh_client.py` |
| 3.4 AI 接口层 | `api_server.py` |
| 3.5 配置与日志 | `config.py`、`logger.py` |

其他堡垒机产品（天玥、网御星云、深信服等）的桥接器，可复制本仓库对应模块，
按第 5 节步骤适配参数解析层后独立成库。
